# Media storage

Status: A local development storage adapter, owner-checked read routes, a dry-run-first orphan audit, and `MediaAsset` metadata lifecycle are implemented. Cloudinary and S3-compatible adapters, signed URLs, and integration with generation jobs are not implemented.

## Current implementation

- `lib/providers/storage/types.ts` defines `put`, `get`, `head`, and `delete` for storage adapters.
- `lib/providers/storage/local.ts` implements local file storage with path traversal checks, non-overwriting writes, and post-write byte/hash verification.
- The authenticated `/api/projects/[projectId]/media` routes list safe metadata and stream an asset only after owner/project checks. They do not expose storage keys or public URLs.
- `npm run media:orphan-audit` lists old local storage objects that have no MediaAsset row. It is a dry run by default. To remove old orphan candidates, pass `-- --older-than-hours=48 --apply`; the minimum allowed age is 24 hours.
- `lib/providers/storage/registry.ts` requires an explicit provider choice. Only `local` is currently supported; selecting `s3` or `cloudinary` fails clearly instead of silently falling back.
- `lib/validation/mediaAsset.ts` checks file signatures against the declared MIME type and asset class, rejects empty/oversized files, calculates SHA-256, and extracts PNG dimensions.
- `lib/providers/media/probe.ts` defines bounded FFprobe inspection and validates audio/video stream metadata. `FFPROBE_PATH` must point to an installed FFprobe binary before a real probe can run.
- `lib/models/mediaAsset.ts` and `lib/repositories/mediaAssetRepository.ts` store owner-scoped metadata, with idempotency and project/type indexes.
- `lib/services/mediaAssetService.ts` checks project ownership, validates bytes, stores and verifies the object, then persists metadata.

Media records are marked `signature_verified`; that means the file header matched its declared type and stored bytes passed size/hash verification. It does **not** mean that a video is playable. FFprobe result parsing is tested, but no FFprobe/FFmpeg executable was found on this machine, so no real media probe has run. The current service does not promote an asset to `playable` or connect it to scene readiness.

The storage service is not yet called by the production worker and no browser upload route exists. The read API is authenticated. Scene/video readiness and final-render gates remain unchanged.

## Local development configuration

Set these manually when you are ready to use local file storage:

```env
MEDIA_STORAGE_PROVIDER=local
MEDIA_LOCAL_STORAGE_DIR=./storage/media
```

The default local root is `storage/media` under the application working directory. That folder is git-ignored. Do not place media under a public web directory. This is development storage, not durable or shared production storage.

S3-compatible environment names are documented in `.env.example`, but credentials alone do not enable an adapter. No S3 or Cloudinary API calls are made by this implementation.

## Keys and idempotency

Keys are generated by the service from a hashed owner identifier, project ID, asset type, and hashed idempotency key. User-supplied paths are not accepted. A retry with the same key and same content reuses the object/asset record; a different file under the same idempotency key is rejected as a conflict.

If object storage succeeds but MongoDB persistence fails, the object may be orphaned. Automated orphan cleanup is not implemented yet. Do not upload large production files until cleanup and retention are implemented.

## Not implemented

- S3/Cloudinary adapters, signed URLs, quotas, retention, and deletion workflows.
- Browser upload and download endpoints.
- Provider output downloading or generation-job integration.
- FFprobe/decoder execution until the executable is installed/configured; playable-media promotion and approval.
- Automatic cleanup of orphaned storage objects.
